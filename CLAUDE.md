# CLAUDE.md

Podman image + launcher for running Claude Code, Snakemake and Jupyter on WSL2 with only the current project folder mounted. See `README.md` for user-facing setup; keep it in sync with any behaviour change.

## Files

- `Dockerfile`: fully qualified `docker.io/library/node:22-slim` (avoids Podman short-name prompts) + Miniforge (conda-forge only) + `@anthropic-ai/claude-code` via npm. Installs git, ssh client, curl/wget, jq, zip/unzip, patch, less, file, nano and build-essential. Sets default git identity via `GIT_AUTHOR_*`/`GIT_COMMITTER_*` `ENV` (`Claude Sandbox <claude-sandbox@localhost>`), marks `/workspace` as a git `safe.directory`, and writes `/etc/ssh/ssh_config.d/claudy.conf` (only `~/.ssh/id_ed25519`, `IdentitiesOnly`, `StrictHostKeyChecking accept-new`). Build arg `WITH_PODMAN` (default 1) installs podman, fuse-overlayfs, slirp4netns and uidmap, adds `root:1:65535` to `/etc/subuid`/`/etc/subgid` and writes `/etc/containers/*` (vfs storage, host netns/pidns/utsns; `BUILDAH_ISOLATION=chroot`). `/dev/fuse` is still passed only with `CLAUDY_NESTED=1`; `entrypoint.sh` rewrites `/etc/containers/storage.conf` on each start (overlay + fuse-overlayfs if `/dev/fuse` exists, else vfs). Build arg `WITH_VSCODE` (default 1) puts the VS Code CLI (`cli-alpine` stable, x64/arm64, unpinned) at `/opt/vscode/code`, not on `PATH`. Copies `etc-claude-code/CLAUDE.md` to `/etc/claude-code/CLAUDE.md`, `vscode-serve.sh` to `/usr/local/bin/vscode-serve` and `git-identity-notice.sh` to `/usr/local/bin/claudy-git-identity-notice`, which `/etc/bash.bashrc` runs in interactive shells with a TTY (so not in Claude's own shells). Appends a channel lock to `/opt/conda/.condarc` (`allowlist_channels` conda-forge/bioconda, `channel_alias`, `custom_channels`, `custom_multichannels`, all `#!final`; `conda env create -f` ignores the allowlist). `PATH` puts `/workspace/.conda_env/bin` first, so `CMD` is the absolute `/usr/local/bin/claude`. `/etc/bash.bashrc` sources `conda.sh` and activates the project env unless `CONDA_PREFIX` is already it and its `bin` is on `PATH`: login shells inherit `CONDA_PREFIX` but get `PATH` reset by `/etc/profile`, and VS Code builds its terminal and extension host environment from one. `CLAUDE_CONFIG_DIR=/claude-config` (named volume holding the login).
- `entrypoint.sh`: runs inside the container on every start. First, if `CLAUDY_PROJECT_DIR` is set, replaces `/workspace` with a link to it and adds it to git's system `safe.directory` (git checks the real path). Then generates the per-project ed25519 key in `/root/.ssh` if missing (printing the public key to stderr), then creates/updates `/workspace/.conda_env` from `/workspace/environment.yml`, then (if the env exists) writes `.conda_env/.gitignore` (`*`, after create/update) and runs `conda activate`, then `exec "$@"`. A stamp file (`.conda_env/.environment.yml.stamp`) records the last successful create/update; a failed create removes the half-built env.
- `claudy`: **runs on the host**, not in the container. Wraps `podman run --pull=never -it --rm` on `localhost/claudy:latest` (fully qualified so a missing image can't resolve to a registry; override `CLAUDY_IMAGE`), mounts `$PWD` → `/projects/<folder>-<8-char sha256 of $PWD>` with `--workdir` there and `CLAUDY_PROJECT_DIR` set (Claude Code files transcripts and memory by working directory, so this keeps projects' `--continue`/`--resume` and memory apart; `entrypoint.sh` replaces the image's empty `/workspace` with a link to it, so `/workspace` paths keep working; images without the `Dockerfile` label `org.claudy.project-dir=1` get the old `/workspace` mount and a rebuild hint), the config volume → `/claude-config` and a per-project SSH volume → `/root/.ssh`. The SSH volume is named `claude-ssh-<folder>-<8-char sha256 of $PWD>` (override: `CLAUDY_SSH`), so moving or renaming a project folder gives it a new key (and a new conversation history). Warns on stderr, waits 5 s for Ctrl-C and still starts when an ancestor of `$PWD` was already a claudy project: its `claude-ssh-<id>` volume exists or it has `.conda_env/.environment.yml.stamp`. Every run passes `--security-opt seccomp=~/.cache/claudy/seccomp.json`, derived (by inline `python3 -I`) from the host's `/usr/share/containers/seccomp.json` (override `CLAUDY_SECCOMP_BASE`): each ALLOW rule for `socket` gets `arg0 != AF_VSOCK` (rules already testing arg0 keep `socket` only if the profile itself denies AF_VSOCK, as Podman 6 does; otherwise they lose it), `socketcall` and `io_uring_*` are dropped, and so are the 32-bit sub-architectures (`archMap`; without `socketcall` libseccomp fails with EEXIST on them; 32-bit x86 is unsupported); it refuses to start if that fails. Don't weaken this: vsock reaches the Windows side of WSL2. Warns (never rebuilds) when `Dockerfile`, `entrypoint.sh`, `vscode-serve.sh`, `git-identity-notice.sh` or `etc-claude-code/CLAUDE.md` in its own repo (found via `readlink -f`) has an mtime newer than the image's `Created`. `claudy pubkey` prints the public key; `CLAUDY_GIT_NAME`/`CLAUDY_GIT_EMAIL` override the image's git identity for one run. `claudy jupyter` publishes `127.0.0.1:8888`. `claudy vscode` publishes `CLAUDY_VSCODE_PORT` (default 8000, 1024-65535) the same way, passes it into the container, mounts the per-project volume `claude-vscode-<folder>-<hash>` at `/root/.vscode-claudy` (never shared: extensions run code) and runs `vscode-serve <port>`. Leading option `--ports 8080,8081` (or `--ports=...`, repeatable) publishes those ports 1:1 on `127.0.0.1` (validated 1-65535, deduplicated with Jupyter's 8888) and passes the list as `CLAUDY_PORTS`. `CLAUDY_NESTED=1` is the only way `/dev/fuse` is passed (plus `label=disable` and a per-project `/var/lib/containers` volume) (same `claudy` image as the default mode); on WSL it refuses unless `/mnt/<drive>` 9p mounts and `WSLInterop` binfmt entries are absent (override `CLAUDY_ALLOW_UNSAFE_NESTED=1`, don't use it).
- `vscode-serve.sh`: runs inside the container for `claudy vscode`. Writes a fresh random connection token to `/run/claudy-vscode-token` (umask 077, never on a command line), prints the token URL (host `vscode-<CLAUDY_PROJECT as a DNS label>.localhost`, because the server's `vscode-tkn` cookie is script-readable, `SameSite=Lax`, host-only and so shared by every port of `localhost`; the server accepts any `Host`) and licence link, splits the commit identity, then `exec`s `code serve-web` on `0.0.0.0:<port>` with `--accept-server-license-terms`, `--disable-telemetry`, CLI and server data under `/root/.vscode-claudy` and the project as default folder. The server itself (several hundred MB) is downloaded by the CLI on first start. Its terminals inherit the container environment, so `claude` runs there with the same login, project path and memory. Identity split: each `GIT_AUTHOR_*`/`GIT_COMMITTER_*` variable still holding the image placeholder is removed from the editor's environment (so Source Control uses git config, with `user.useConfigOnly=true` via `GIT_CONFIG_COUNT` so it refuses rather than guesses) and written back for terminals and the Claude Code extension into `/root/.vscode-claudy/server/data/Machine/settings.json` (`terminal.integrated.env.linux`, `claudeCode.environmentVariables`; those four keys are replaced on every start, other settings kept, via `jq`). If that file isn't plain JSON, it warns and leaves the editor with the placeholder. Then runs `claudy-git-identity-notice --editor`. VS Code resolves the extension host's environment from a login shell, so the placeholder must not come back through `/etc/bash.bashrc`.
- `git-identity-notice.sh`: runs inside the container (from `vscode-serve` and interactive `bash`). Silent outside a git repository. In terminals, prints a stderr notice while `git var` shows the `Claude Sandbox` placeholder author or committer, since commits made outside Claude get no warning from it: under `claudy vscode` (`CLAUDY_VSCODE_PORT` set) that the terminal and Claude use the placeholder while Source Control uses git config, else the `claudy bash` restart command with `CLAUDY_GIT_*`. With `--editor` (from `vscode-serve`), says which identity Source Control commits as, or how to set one.
- `etc-claude-code/CLAUDE.md`: instructions for the agents running *inside* the container (sandbox rules, nested podman recipe). Meant to be installed at `/etc/claude-code/CLAUDE.md` (Claude Code's managed-policy location, applies to all projects) by a `COPY` in the `Dockerfile`. Keep it in sync with the security model below.
- `new-claudy-distro.ps1`: **runs on Windows.** Creates the dedicated, trimmed WSL distro (README *Dedicated WSL distro*): `wsl --install --name --no-launch`, user with UID 1000 and password, `/etc/wsl.conf`, `wsl-remove-interop.service` (removes the `WSLInterop` binfmt handler at boot; WSL registers it even with interop disabled, and it fires inside containers), Podman/git/vim, guard rails against running code on the distro (apt pin `claudy-no-dev-tools.pref` at priority -1 for SSH and dev tools, `/etc/claudy-host.bashrc` prompt marker, warnings and a one-time welcome (`claudy-help`) sourced from `/etc/bash.bashrc`, `claudy-tmp-noexec.service` for `/tmp`, `/dev/shm` and `/run/shm` plus apt's `ExtractTemplates::TempDir` `/var/tmp`; never make `~/projects` noexec, the container's `/workspace` would inherit it), package trim (keep list marked manual, metapackages `ubuntu-wsl`/`ubuntu-minimal` removed, then leftover extras, including `ubuntu-insights` (only recommended by `wsl-setup`; removing it skips the first-start metrics question), that wouldn't take a keep-listed or Essential/required package along, then `autoremove --purge`), isolation check after restart, clone (`-Branch`, default `main`) + build + `~/bin/claudy`. Embedded bash is piped into `wsl.exe` (CR stripped, trailing `exit 0`). Its keep/meta/extra lists must match the README's *Trim the distro*, and the guard rails its *Guard rails* section. Untested: no PowerShell or WSL in the container; changes need the user's review like `claudy`.
- `environment.yml`: example/test project env. Per the README, real projects carry their own.

## Security model (do not weaken)

The full threat model and known limitations are in `SECURITY.md`; keep it in sync when changing mounts, capabilities, networking, nested mode or the image's supply chain. It is written for the user: read it here to maintain it, never as a list of things to try. Keep it free of recipes (exact commands, failure conditions, bypass mechanisms, file locations), keep the note for agents at its top, and don't copy it into the image or point the in-container instructions (`etc-claude-code/CLAUDE.md`) to it.

- The container sees only `/workspace`, `/claude-config` and its own `/root/.ssh`. No host SSH keys, git credentials, Windows drives or extra mounts. The only mounts are `$PWD`, the config volume and the per-project SSH volume (one key per project, used as a GitLab *deploy key*; never mount host `~/.ssh` or an agent socket). Don't add other `-v`, `--privileged`, host networking, or port bindings on `0.0.0.0`.
- SSH keys are per project (one volume each) so containers can't cross-talk. Recommended use is a GitLab *deploy key* on a single repository, never a user-account key. The private key is readable by Claude; don't hide that in docs. The user gets the public key only from `claudy pubkey` on the host, never from Claude in a session (a key shown by a misled session could be someone else's); `etc-claude-code/CLAUDE.md` tells agents to refuse.
- **Nested mode is opt-in and off by default.** Never pass `/dev/fuse`, extra capabilities, `--privileged`, an unconfined seccomp profile or a host podman socket (a socket allows mounting any host path) in the default mode. In nested mode, pass only `/dev/fuse`. Don't remove the WSL check in `claudy`: the intended deployment is a dedicated WSL distro with `[automount] enabled=false` and `[interop] enabled=false` (README "Dedicated WSL distro"), because an escape from a WSL2 container reaches the Windows files and programs of the user.
- **Claude may change its running container but not the sandbox definition.** In-container changes (apt, `/etc`) don't persist; anything a project needs again is set up and documented in that project, in its own convention (conda `environment.yml`, `pyproject.toml`/`setup.py`, a `Dockerfile`, README), never in shared storage such as `/claude-config` (see `etc-claude-code/CLAUDE.md`). Never edit `claudy`/`Dockerfile`/`entrypoint.sh` when this repo is mounted without the user's review. Never ask the user for their `sudo` password and never use `sudo` outside the container; if a task needs a rebuild, a package in the image, or a change to `claudy`/`Dockerfile`/`entrypoint.sh`, describe the change and ask the user to review and apply it from their own terminal outside `claudy`. Nested containers (inner `/var/lib/containers` volume) are fine for development work.
- Docs and scripts in this repo are public. Never add secrets, hostnames, usernames, project/dataset names or key material to any file here. Changes to `SECURITY.md`, `README.md` and `CLAUDE.md` weakening a stated protection need explicit user review, like code changes.
- Ports bind to `127.0.0.1` only.
- Conda channels: `conda-forge` and `bioconda` only. Never add Anaconda `defaults` (ToS/licensing).
- Never set or rely on `ANTHROPIC_API_KEY`; auth is the Claude Team subscription login stored in the volume.
- Network is unrestricted. That's a documented limitation, not something to "fix" silently.
- **Trust boundary:** when this repo itself is the mounted `/workspace`, Claude can edit `claudy`, which the user runs on the host (it's symlinked into `~/bin`). Treat changes to `claudy` and `Dockerfile` as needing explicit user review. The README's intended layout keeps this repo outside any project folder.

## Working here

- You are likely running inside this image as root (rootless Podman maps that to the host user). `podman` is installed in the image and works without `/dev/fuse` (vfs; `entrypoint.sh` switches to overlay + fuse-overlayfs when `/dev/fuse` exists); you must not build or run *this* image to test sandbox changes; validate with `bash -n` and by running scripts against a temp copy (e.g. `sed` the `/workspace` paths to a scratch dir).
- Changes to `entrypoint.sh` or `Dockerfile` take effect only after the user rebuilds: `podman build -t claudy .`.
- Git commits from the container use the env-var identity above; don't write a host `~/.gitconfig` or credentials into the image or volumes.
- Scripts use `set -euo pipefail` and bash arrays for argument lists; keep that style.
- `.conda_env/` and `*:Zone.Identifier` (Windows download metadata) are gitignored.

1. **`claudy` hardening**
   - The `$PWD` guard refuses only `/`, `$HOME`, `/mnt/c` and `/mnt/c/Users/*`. Extend it to every Windows drive and every path under it (`/mnt/[a-z]`, `/mnt/[a-z]/*`) and to ancestors of `$HOME` (e.g. `/home`).

   - Add `--security-opt no-new-privileges`: compatible with the root-in-container design (apt and nested Podman as root need no setuid helpers), but it would break a non-root nested Podman (see item 5).
   - Drop capabilities nothing uses, e.g. `--cap-drop` `NET_BIND_SERVICE`, `SETFCAP`, `SETPCAP`. Keep `CHOWN`, `DAC_OVERRIDE`, `FOWNER`, `SETUID`, `SETGID`, `KILL`, `SYS_CHROOT` (apt, conda, nested Podman); `--cap-drop=ALL` breaks apt and nested Podman. Check conda env creation, npm, `apt-get install` and a nested `podman run` afterwards.

4. **Two users in the dedicated distro: `admin` and `claudy` (design, not started).** Today one user both runs `claudy` and has `sudo`. A container escape lands as that user, and from there the `sudo` password is one prompt away: anything running as that user can intercept what is typed in its shells. Root in the distro can mount the Windows drives again (tested), so that password is all that separates an escape from the Windows files. Root-owned files alone don't help while the escaped user can phish the password, and hardening the dotfiles (`chattr +i` on `.bashrc`, `.profile`, `.bash_profile`, `.bash_login`, `.inputrc`) leaves too many other ways in (`crontab`, `~/.config/systemd/user`, `~/.config/containers`, the rootless image store, `~/bin` on `PATH`). Instead, separate the roles:
   - **`claudy` user** (WSL default user, UID 1000): runs `claudy`, owns `~/projects`, has the subuid range for rootless Podman. Not in `sudo` (no password at all, so nothing to phish), no `~/bin` on `PATH`.
   - **`admin` user**: in `sudo`, with the password. Entered only from PowerShell with `wsl -d <name> -u admin` (or `-u root`), never with `su`/`sudo` from the `claudy` user's shell, which a compromised `claudy` user could fake. No subuid range, so rootless Podman doesn't work for it.
   - **`admin` must not run `claudy`**: `/usr/local/bin/claudy` refuses unless it runs as the user named in root-owned `/etc/claudy/user` (and refuses any user in the `sudo` group), so the wrong user can't start a sandbox by mistake. The `admin` shell gets the `[claudy host]` nudge plus a reminder to switch users.
   - **Root-owned launcher and definition**: the repository is cloned to `/opt/claudy` (root-owned; `admin` pulls and reviews `git diff` there with `sudo`), `claudy` installed with `install -o root -m 755` to `/usr/local/bin`. A root-owned helper (e.g. `/usr/local/sbin/claudy-rebuild`, run by `admin` with `sudo`) builds the image as the `claudy` user (`runuser -u claudy -- podman build -t claudy /opt/claudy`, so it lands in that user's rootless store) and records the image ID in `/etc/claudy/image-id`.
   - **What the `claudy` user can still tamper with, and how `claudy` copes**: its rootless image store (`claudy` refuses to start unless `podman image inspect` of `claudy` matches `/etc/claudy/image-id`, which it can't forge) and `~/.config/containers` (`claudy` sets `CONTAINERS_CONF`, `CONTAINERS_STORAGE_CONF` and `CONTAINERS_REGISTRIES_CONF` to root-owned files in `/etc/claudy/`, so no extra default mounts). Its own crontab and user units remain, but only with its own rights.
   - **Keep single-user setups working**: plain Linux and an everyday WSL distro with Windows drives and interop (README *Where to run it*) can't or won't have the two users, the root-owned `/opt/claudy` or the guard rails. So the layout is opt-in (a `new-claudy-distro.ps1` option or the default only there), and `claudy` enforces the user check, pinned Podman config and image ID only when `/etc/claudy/user` (or a similar root-owned marker) exists; without it, today's behaviour, launcher in `~/bin`, image built by the user. Document both paths in the README without making the simple path harder to follow.
   - Small step that can go first: `claudy` refuses to run when `$PWD` is the claudy repository, inside it, or an ancestor of it (it can find its own location through the `~/bin` symlink).
   - Changes: `new-claudy-distro.ps1` creates both users (asks for `admin`'s password only), sets `default = claudy` in `wsl.conf`, removes `admin`'s subuid entries, installs `/opt/claudy` and the helper, runs the first build through it. README: setup and update steps (`wsl -u admin` from PowerShell, then `sudo claudy-rebuild`), Explorer path `\\wsl.localhost\<name>\home\claudy\projects`, *Keep Claude away from the distro itself*. `SECURITY.md`: replace the single-user wording. Needs the user's review like any `claudy` change. Keep it optional or well-explained: most users set this up once by following the script.
5. **Non-root container user and per-project subuids (design idea, not started)**: today the container runs as in-container root, which rootless Podman maps to the host user, so a container escape lands as the user. Instead, a host-side setup script (run by the user, outside `claudy`, with `sudo` only for `/etc/subuid`) would allocate a distinct subuid range per project, create/prepare the project folder for it and print the matching launch options. `claudy` (or a separate launcher, e.g. `claudy-init` plus `claudy`) would then pass `--uidmap`/`--gidmap` (or `--subuidname`) for that project, plus a `USER` and home in the `Dockerfile`.
   - Benefit: an escape yields an unprivileged subuid that owns nothing else; projects cannot share a uid on the host.
   - Open problems: files created in the container are then owned by the subuid, so the user needs `podman unshare` or POSIX ACLs (`setfacl -R -m u:<user>:rwx` plus default ACLs on the project folder) to edit them from WSL; check that git on the host copes (`safe.directory`/dubious ownership) and that ACLs work on the WSL ext4 filesystem (not on `/mnt/<drive>`).
   - A non-root user *inside* the container gains little on its own: with `--userns=keep-id` it maps to the same host user as container root does today, so an escape lands in the same place, and any process can still create a user namespace with full capabilities inside it (nested Podman needs that), which is the main kernel attack surface. It mainly helps against runtime escapes that need container root. Nested Podman as non-root also needs setuid `newuidmap`/`newgidmap` (no `no-new-privileges`, no `nosuid`) and its own subuid range carved out of the container's 65536 ids. The value is in the host-side per-project subuid part.
   - Simpler first step: `USER node` with `--userns=keep-id` (host uid = container uid, no ACLs needed).
